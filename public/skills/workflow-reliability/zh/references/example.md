# 工单超时：状态转换与恢复决定

虚构演练场景。下面是执行前的设计，不是真实故障日志，也未连接工单系统。

## 事件与副作用

- 事件：来源服务来信；同一封来信的稳定事件 ID 不随重试改变。
- 副作用：人工批准后创建一张测试工单。
- 回执：目标工单 ID、最终状态、执行记录关联键。
- 尚需核对：目标是否支持幂等键、键的有效期、查询一致性，以及批准后内容变更是否需要重新审批。

## 状态转换

| 当前状态 | 证据 | 下一步 |
| --- | --- | --- |
| 待审批 | 草稿与输入摘要 | 批准后进入待执行；拒绝则结束，不写入 |
| 待执行 | 有效审批与稳定事件标识 | 查询已有结果；未完成时执行已批准动作 |
| 明确成功 | 有目标记录 ID 与成功回执 | 保存结果；重复事件直接返回已有回执 |
| 明确失败且未写入 | 目标确认拒绝或可证明未创建 | 根据错误类型修正或有限重试 |
| 状态未知 | 超时，无可确认回执 | 进入待对账，不能当作未执行 |
| 部分完成 | 已有部分子项的目标记录 | 保留已完成子项，只恢复未完成部分 |

## 超时恢复流程

1. 用稳定事件标识或目标查询字段查找已创建记录。
2. 查到且内容符合已批准请求：保存已有回执，结束此次恢复。
3. 确认未创建且错误可重试：在业务同意的次数及总时限内重试。
4. 无法确认状态：转接管人，不自动重建。不要因为一次查询暂时查不到就假定没有写入。

## 待执行演练

模拟目标写入成功但响应丢失，再重放同一事件。预期最终只有一张工单，并能定位原始审批和回执。另测拒绝审批、持续不可用、部分成功和审批后内容变更。每项记录执行环境、实际结果与接管决定，不把设计中的预期写成通过。
