## 先把结论摆出来

企业 AI POC 的目标不是证明模型会回答，而是证明一条业务链在真实约束下值得继续投入。聊天窗口可以展示模型能力，却回答不了五个决定项目生死的问题：数据归谁、谁有权看、错误怎样被发现、失败后谁接管、效果怎样验收。

因此，售前方案不能从模型名单开始。它应从任务、证据和责任开始。

## 资格判断：什么问题值得做

我会先把需求压缩成一页资格卡，至少回答以下问题：

1. **业务任务**：用户原本要完成什么动作，现有流程卡在哪里？
2. **输入与输出**：输入是文档、表格、图像、语音还是系统事件；输出是建议、结构化字段还是可执行动作？
3. **错误成本**：答错、漏答、越权或误操作会造成什么后果？
4. **证据条件**：有没有可用的历史样本、标准答案和失败样本？
5. **系统边界**：哪些系统只能读取，哪些允许写入，谁能批准高风险动作？

如果这五项长期处于“后面再说”，POC 多半会变成无边界演示。相反，即使模型选型尚未确定，只要任务和验收对象清楚，方案仍然可以推进。

## RAG：先测检索，再测回答

RAG 的结果由解析、切片、索引、召回、重排、上下文组织和生成共同决定。只看最终回答，会把检索漏召回、版本过期和生成编造混成一个问题。

最低限度应拆成三层评测：

| 层级 | 要回答的问题 | 代表指标 |
| --- | --- | --- |
| 数据与解析 | 原始内容是否完整进入索引 | 解析成功率、表格/页码保留、增量更新时间 |
| 检索 | 证据是否被找回并排在可用位置 | Recall@K、Precision@K、重排前后差异 |
| 生成 | 回答是否忠于证据并覆盖问题 | 有据性、引用覆盖、关键事实准确率、拒答正确率 |

黄金测试集不能只放“容易答对”的问法。应包含简称、错别字、跨文档问题、版本冲突、权限隔离、无答案问题和带有提示注入的文档。这样测出来的结果才接近上线后的负载。

## Agent：每个动作都要有权限和回退

Agent 的风险不在于它能不能调用工具，而在于调用后的状态是否可解释、可撤销。方案中应给每个工具写清：读写权限、参数校验、幂等要求、超时、重试、审批点、审计日志和补偿动作。

对高风险动作，我倾向采用“模型提议、规则校验、人工批准、系统执行”的结构。它没有全自动演示那么抢眼，却更容易通过安全、合规和业务负责人的审查。

以下情况必须触发人工接管：

- 缺少决定性字段，且无法从授权数据源补齐；
- 不同来源对关键事实冲突；
- 工具返回部分成功或状态不明；
- 操作涉及外发、删除、付款、审批或客户承诺；
- 输出置信度、引用覆盖或规则检查低于阈值。

## 架构不是一张模型连线图

可交付架构至少包含六层：渠道与身份、应用编排、模型与路由、知识与数据、工具与业务系统、评测与运维。每一层都要列出所有者、接口、部署位置、数据范围和故障影响。

模型可以替换，但身份、权限、审计和业务接口通常不能临时拼装。把这些工作推迟到 POC 之后，会让一个“效果不错”的演示在进入 IT 评审时重新归零。

## 成本要按任务算

“每百万 token 多少钱”不能直接回答项目预算。更有用的口径是单任务成本：模型调用、向量检索、文档解析、存储、重排、工具调用、人工复核和失败重试加总，再乘以并发、峰值和保留周期。

同样，时延也应拆开测。检索慢、外部接口慢和模型生成慢，对应完全不同的优化动作。总时延只有一个数字，无法指导交付。

## 一份可签字的验收表

POC 开始前，业务、技术和项目负责人应确认同一张验收表：

| 项目 | 示例口径 |
| --- | --- |
| 样本范围 | 指定业务域、文档版本、权限角色和异常样本 |
| 质量指标 | 关键事实准确率、引用覆盖率、拒答正确率 |
| 性能指标 | P50/P95 时延、并发量、超时率 |
| 安全指标 | 越权测试、提示注入、敏感信息外泄、工具误调用 |
| 运维指标 | 日志可追踪、版本可回滚、知识可更新、异常可接管 |
| 退出条件 | 哪些失败意味着停止，哪些问题允许进入下一阶段解决 |

验收指标不必多，但必须能被双方重复执行。一个指标若只能由方案方解释、客户无法复测，就不是合格的验收标准。

## 售前最后应交付什么

完整的 POC 包不止一份 PPT。它至少包括资格卡、范围说明、架构图、数据清单、接口清单、测试集、指标定义、风险登记、演示脚本、失败脚本、成本估算、实施计划和验收记录。

这套做法会让前期显得更慢，却能更早暴露那些真正昂贵的问题。企业 AI 项目最怕的不是模型能力差，而是所有人都以为别人会负责数据、权限、异常和验收。
