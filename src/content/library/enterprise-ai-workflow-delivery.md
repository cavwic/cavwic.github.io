## 先决定交付什么，而不是先决定用哪个模型

本方案是基于公开资料整理的设计方法，不是客户实施案例。适用于内部知识助手、文档字段提取、工单分流和业务草稿生成；不把医疗、信贷或其他高影响决策作为可直接自动化的默认场景。

先写清一句任务：谁收到什么输入，要向哪个系统交付什么输出，出错后由谁处理。比如“服务人员根据授权维修手册，生成带出处的答复草稿，由值班工程师确认后发送”，比“建设企业智能体平台”更容易划定边界。

| 业务任务 | 最小可交付结果 | 不应默认交给模型的部分 |
| --- | --- | --- |
| 内部知识查询 | 带文档版本与定位的回答，或明确拒答 | 身份认证、文档授权、知识有效期 |
| 文档处理 | 字段、原文位置、缺失项与人工修订记录 | 必填校验、金额计算、业务主键 |
| 工单处理 | 分类建议、责任团队与答复草稿 | 权限授予、不可逆状态变更 |
| 经营资料整理 | 有来源的事实摘要与待确认事项 | 财务真实性认定、对外承诺 |

## 一个可解释的最小架构

输入进入后，先由身份与规则层判断任务能否执行，再读取授权范围内的数据。模型只负责需要语义理解的步骤；格式、数值和状态转换交给确定性校验。校验失败进入待处理队列，不把“能生成文字”当成业务成功。

知识问答可以使用 RAG，但结构化库存、订单或实时状态更适合调用授权查询接口，而不是把旧快照当事实。Microsoft 的 RAG 文档将内容准备、检索相关性和访问控制分开讨论；这也提示我们不要用回答效果掩盖数据治理问题。[官方参考](https://learn.microsoft.com/en-us/azure/search/retrieval-augmented-generation-overview)

一个最小闭环可以是：提交任务 → 校验身份及输入 → 查询证据 → 生成草稿 → 规则检查 → 人工审批 → 受控写入 → 返回回执。每一步传递同一个任务标识，但仅传递下游需要的字段。

## 固定工作流和 Agent 的分界

已知路径的业务流转优先采用固定步骤。只有当下一步确实依赖运行时判断，且工具边界和停止条件已经明确，才引入模型动态规划。Anthropic 对 workflow 与 agent 的区分可作为概念参考；具体平台能力和许可证应另行核对。[模式参考](https://www.anthropic.com/research/building-effective-agents)

我建议先从“模型给建议，系统保留状态机”开始。这样业务负责人能看到谁批准了哪次动作，而不必从一段模型对话推断业务状态。

## 写入动作必须有单独的契约

每个写入节点至少定义：目标系统、允许操作、业务主键、审批人、超时、重复执行策略、回执字段和补偿方式。尤其需要区分以下情况：

- **明确失败**：尚未写入，可修正后重试。
- **明确成功**：保存目标记录标识，再次触发时查询或复用结果。
- **状态未知**：请求超时但可能已完成，先对账，禁止直接重复创建。
- **部分成功**：记录已完成的子项，只恢复剩余项或执行已批准的补偿。

错误通知不等于恢复机制。n8n 提供错误工作流和失败执行记录，但业务侧仍需设计重复提交、外部超时和状态核对。[错误处理文档](https://docs.n8n.io/build/flow-logic/handle-errors-gracefully)

## 把验收拆成三张表

**业务样本表**记录正常、缺字段、冲突、越权、过期资料、重复事件和下游不可用样本，标明预期结果及复核人。数量由风险和业务覆盖决定，不把固定样本数当成充分性保证。

**运行指标表**分别记录任务成功、人工修订、错误路由、P95 时延、单任务成本和异常队列积压。人工纠正也要计入成本，不能只统计模型调用费用。

**上线条件表**规定谁能放行、哪些失败必须阻断、如何回滚提示词或知识版本，以及谁在业务时间之外接管。模型、检索配置、提示词和接口版本要能关联到一次执行。

## 防护不是一句提示词

外部文档、网页和工单内容是待处理数据，不能授予系统权限。RAG 也不能消除提示注入；最小权限、输出校验和高风险审批应由程序落实。[OWASP 风险说明](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)

本方案的判断是：如果当前仍没有数据负责人、失败接管人或可复测样本，就先完成离线演练，不应把流程接入生产写入端。
