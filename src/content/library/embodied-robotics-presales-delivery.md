## 演示顺利，不等于方案成立

机器人演示通常把环境整理到最有利状态：路线固定、物体摆正、网络稳定、人员配合。客户现场恰好相反。地面有接缝，光照会变，人会穿行，上游会延迟，对象会放反，电梯和门禁会失联。

因此我把“失败脚本”视为机器人方案的一部分。方案必须说明机器人在哪些条件下会停、会重试、会绕行、会请求人工，以及如何回到可继续执行的状态。只展示成功路径，无法判断系统能否交付。

## 场景资格：先判断值不值得用机器人

现场勘察不是量一遍通道宽度。它要确认任务为什么存在、谁在做、何时发生、上下游怎样交接，以及失败会影响谁。

一份场景资格表至少包含：

- **任务对象**：尺寸、质量、材质、可变范围、摆放误差、是否易碎或危险；
- **空间条件**：通道、坡度、地面、门、电梯、工作台、禁入区和人员动线；
- **节拍条件**：平均节拍、峰值、等待、换班、充电、维护和异常恢复；
- **系统条件**：网络、地图、WMS/MES/门禁/电梯接口、时钟和身份体系；
- **安全条件**：人员暴露、危险源、急停、保护停止、隔离与现场责任人；
- **服务条件**：备件、远程支持、到场时限、培训、版本和变更管理。

如果固定工装或简单自动化能更稳定地完成任务，就不应为了“具身”而增加系统复杂度。售前的价值也包括及时否定不合格机会。

## 把任务写成状态机

“机器人去拿货并送到工位”不是可测试任务。状态机可以把它拆成：待命、接单、资格校验、导航、目标识别、抓取、确认、运输、交付、回执、充电。每个状态都应有进入条件、完成条件、超时、重试次数和退出路径。

例如抓取失败不能只写“自动重试”。至少要区分目标未检出、姿态不可达、碰撞风险、夹持不稳、对象滑移和传感器异常。不同失败原因需要不同动作；盲目重复只会扩大风险。

## 本体选型要服从任务

机器人参数不能单独比较。载荷要结合手臂伸展、加速度和末端工具；续航要包含计算、传感器、等待和充电策略；工作范围要考虑姿态、碰撞和可达性；速度要在安全限制和成功率下评估。

本体之外，方案还要明确：

1. 感知是在机器人端、边缘端还是云端运行；
2. 任务系统怎样下发命令并确认状态；
3. 地图、模型、策略和配置如何版本化；
4. 哪些接口由厂商提供，哪些由集成方或客户负责；
5. 网络中断、服务异常和局部故障时，机器人停在哪里。

公开资料没有说明的参数应写“未公开”，进入询证清单。把未知写成默认能力，是售前阶段最危险的省事方式。

## 安全不能放在附录

工业机器人和协作机器人有相应安全标准入口，但具体项目仍需要结合设备、任务和现场进行风险评估。标准页面不能替代完整标准文本，也不能替代合格人员的现场判断。

方案至少应标出危险区域、人员接近方式、急停位置、保护性停止条件、恢复权限和维护锁定流程。对于带机械臂、移动底盘或灵巧手的系统，还要考虑夹点、挤压、跌落、倾覆、失控运动和电池风险。

安全不是一句“配备避障”。避障解决的是一部分感知与规划问题，不能覆盖机械、电气、控制、程序和操作流程中的所有危险。

## POC 不是现场试试看

机器人 POC 应在进场前确定对象集、场地版本、任务次数、人员角色和数据记录方式。一个可执行的验收矩阵可以包括：

| 维度 | 应记录的证据 |
| --- | --- |
| 任务成功 | 每次状态、失败位置、人工干预和最终结果 |
| 节拍 | 正常、峰值、等待与恢复后的全周期时间 |
| 导航 | 路线完成率、阻塞、重规划和定位丢失 |
| 操作 | 识别、可达、抓取、保持、放置和对象损伤 |
| 安全 | 触发条件、停止距离、恢复权限和日志 |
| 稳定性 | 连续运行、充电、温升、网络波动和软件重启 |
| 服务 | 故障定位时长、备件、远程支持和现场响应 |

所有数据都应保留失败样本。只把成功视频剪在一起，会失去最有价值的交付证据。

## 报价前要列责任矩阵

具身机器人项目常同时涉及本体厂商、算法团队、集成商、客户 IT、现场设备方和业务部门。每个接口若没有所有者，最后都会落到项目经理身上。

责任矩阵应覆盖现场改造、网络、电源、地图、接口、对象标准化、安全评估、培训、备件、版本升级和验收签字。报价中的每项资源都要对应一个交付动作；没有对应动作的“实施服务费”难以解释，也难以验收。

一份专业方案不会承诺机器人无所不能。它会清楚说明系统在什么条件下能做什么，做不到时怎样退出，以及进入下一阶段前还缺哪条证据。
