## 一个常被忽略的超时

假设模型把来信分类后，工作流向工单系统发出创建请求。目标已经写入，但响应在网络中丢失。调用方看到超时，如果直接重试，可能创建第二张工单。这个例子是设计推演，不是实际事故记录。

问题不在于是否设置三次重试，而在于超时之后不知道业务状态。重试适合恢复暂时故障；幂等和对账才负责避免重复副作用。

## 先给事件一个稳定身份

使用来源事件标识或经业务确认的组合主键，而不是每次重试都重新生成身份。目标接口支持幂等键时，应确认其作用范围、保存期限和参数不一致时的行为。不支持时，需要本地执行记录与目标查询配合；不能仅凭内存里的“已经执行”标记保证可靠性。

| 当前状态 | 下一步 |
| --- | --- |
| 未发送 | 校验后执行 |
| 明确拒绝且未落库 | 按错误类型修正或有限重试 |
| 超时且状态未知 | 查询目标记录，无法确认时转人工 |
| 已完成 | 返回已有结果，不重复创建 |
| 部分完成 | 核对已完成子项，只恢复未完成部分 |

## 错误分支还需要业务信息

平台错误日志告诉我们哪个节点失败，不一定知道业务动作是否已经发生。n8n 的错误工作流可以集中处理执行失败，但通知中仍应包含脱敏后的任务标识、失败节点、状态和接管入口，而不是把全部原文或密钥发送出去。[官方错误处理说明](https://docs.n8n.io/build/flow-logic/handle-errors-gracefully)

补偿也不是“删掉刚才创建的东西”那么简单。下游可能已经读取、审批或对外发送。需要由业务定义可补偿的状态，不能把每个动作都当成可逆。

## 怎么验收恢复能力

在测试环境重放相同事件、模拟响应丢失、从审批前后分别中断，再验证目标记录数量、回执和审计链。设置最大尝试次数和截止时间，禁止无限循环。恢复后保留失败与修复记录，不把重新跑通当成从未失败。

我的判断是：一个只展示成功路径的工作流，还没有证明它可交付。先用 [工作流恢复设计 Skill](/skills/workflow-reliability) 写出状态契约，再把它接入选定平台；[AI 交付工作台](/tools/ai-delivery-workbench) 可以保存这份交接材料，但本身不执行外部写入。
