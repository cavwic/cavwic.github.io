# 工作流恢复设计

从业务事件和目标状态开始，不从节点截图开始。允许沿用用户选定的平台；不把固定路径全部改成自主 Agent。

## 工作方式

1. 对每个步骤记录输入、输出、读写性质、负责人和失败状态。询问真实业务主键；不把每次调用生成的新 UUID 当作天然幂等。
2. 对写入或外发单独标注实际审批、最小权限、目标回执和执行前条件。文档里的勾选只是设计，不是批准。
3. 区分明确失败、明确成功、状态未知和部分完成。超时可能发生在目标成功之后；先查询对账，再决定重试，无法确认则转人工。
4. 明确重试错误类型、次数和总时限；不会因权限错误而无限重试。补偿按业务可逆性设计，不能假定删除即可恢复原状。
5. 在隔离环境安排重复事件、响应丢失、审批前后中断和部分成功测试。输出恢复记录格式与待验证项，不伪造已执行日志。

## 专项产出

交付有副作用的节点清单、状态转换表、写入契约与恢复演练。对状态未知单独给出查询、证据、责任人与停止条件，不能用“重试”覆盖所有失败。

用 [状态与恢复工作表](references/recovery.md) 与 [工单超时完整演练](references/example.md) 记录细节。`brief.example.json` 是工单设计示例；`brief.blank.json` 用于新任务。工作台 JSON 不是 n8n、Dify 或其他平台可直接导入执行的流程。

Node.js 22.6+：`node scripts/validate-brief.mjs brief.example.json --locale zh`。仅接收 workflow 模式。退出码 0 只表示有限表单检查通过；1 表示缺项，2 表示模式、文件或格式错误。检查不会执行请求，也不能证明目标接口支持幂等。

参考：[n8n 错误处理](https://docs.n8n.io/build/flow-logic/handle-errors-gracefully)。
